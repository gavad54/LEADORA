# چک‌لیست آمادگی تولید و انتشار تجاری LEADORA

این سند وضعیت کارهای لازم را از مواردی که صرفاً با موفقیت CI اثبات می‌شوند جدا می‌کند. تیک‌ها فقط پس از مشاهده شواهد واقعی زده شوند. این چک‌لیست جایگزین آزمایش یا تأیید مالک نیست.

## 1. حفاظت از داده و محیط تولید
- [ ] تأیید شود `LEADORA_ENV=production` و `LEADORA_SECRET` یک مقدار تصادفی قوی، پایدار و محرمانه است؛ مقدار secret در گزارش‌ها یا چت نمایش داده نشود.
- [ ] تأیید شود volume پایدار در `/data` متصل است و پایگاه داده در همان volume قرار دارد.
- [ ] نسخه پشتیبان خارج از volume/میزبان اصلی، رمزگذاری‌شده و با دسترسی محدود پیکربندی شود.
- [ ] بازیابی نسخه پشتیبان روی محیط جداگانه آزمایش شود؛ هرگز برای آزمایش، پایگاه داده تولید را بازنشانی نکنید.
- [ ] سیاست نگهداری، کنترل دسترسی و حذف امن نسخه‌های پشتیبان مستند شود.

## 2. مالک سامانه و مالک شرکت
- [ ] مالک مجاز، ایمیل دقیق و مورد تأیید حساب مالک را مستقلاً مشخص کند.
- [ ] مدیر مجاز، `LEADORA_OWNER_RECOVERY_TOKEN` را با توکن تصادفی مستقل و `LEADORA_OWNER_RECOVERY_EMAIL` را در تنظیمات امن Railway ثبت کند؛ توکن نباید با توکن bootstrap یکسان باشد.
- [ ] شناسه مالک سامانه فقط پس از احراز هویت و تأیید مستقل تعیین شود؛ شناسه یا ایمیل حدس زده نشود.
- [ ] ورود مالک سامانه با حساب واقعی و مجاز آزمایش شود.
- [ ] ورود مالک شرکت با حساب جداگانه آزمایش شود.
- [ ] بررسی شود مالک شرکت به اطلاعات شرکت دیگر و قابلیت‌های مالک سراسری دسترسی ندارد.
- [ ] نشست منقضی، توکن نامعتبر، کاربر ناشناس و تلاش بازیابی ناامن باید رد شوند.
- [ ] نتیجه آزمون‌ها بدون افشای اطلاعات شخصی یا اسرار ثبت شود.

## 3. اعتبارسنجی مالی
- [ ] قرارداد فعال، واحد پول، دوره مالی و تعریف هزینه مستقیم توسط طرفین تأیید شود.
- [ ] فروش خالص = فروش ثبت‌شده - تخفیف - برگشت فروش؛ بهای تمام‌شده و هزینه مستقیم با اسناد منبع تطبیق داده شوند.
- [ ] آزمون مستقل برای مقادیر صفر، منفی، تکراری، اعشاری، مرز دوره و داده ناقص انجام شود.
- [ ] گزارش تأییدشده بدون گردش اصلاحیه قابل بازنویسی نباشد.
- [ ] جمع گزارش‌ها با محاسبه مستقل و نمونه اسناد واقعیِ مجاز تطبیق داده شود.
- [ ] تأیید حسابدار/مشاور حقوقی برای استفاده در تسویه واقعی اخذ شود.

## 4. قابلیت اطمینان و اتصال‌ها
- [ ] تمام مسیرهای اصلی با نقش‌های مجاز و غیرمجاز آزمایش شوند.
- [ ] ورود CSV، مدیریت تکراری‌ها، فاکتور، پرداخت جزئی، هزینه، سفارش، فرصت فروش و خروجی‌ها به‌صورت انتها‌به‌انتها آزمایش شوند.
- [ ] خطا و قطع سرویس‌های بیرونی، timeout، retry و محدودیت نرخ آزمایش شوند.
- [ ] اتصال‌های فاقد API یا مجوز رسمی به‌عنوان «غیرفعال» نمایش داده شوند؛ از ادعای اتصال زنده خودداری شود.
- [ ] آزمون بار و آزمون پایش 5xx، latency، فضای دیسک و سلامت SQLite انجام شود.
- [ ] پس از هر استقرار، `/api/health` و لاگ‌های سرویس بررسی شوند.

## 5. انتشار تجاری Android
- [ ] کلید امضای انتشار پایدار در اختیار مالک قرار گیرد و در Git/چت/log ذخیره نشود.
- [ ] کلید و رمز آن در GitHub Actions Secrets یا مخزن اسرار مناسب ثبت شوند.
- [ ] workflow انتشار از debug signing جدا باشد؛ release باید با کلید پایدار امضا شود.
- [ ] امضای APK/AAB، شناسه بسته، نسخه و SHA-256 بررسی شود.
- [ ] نصب تازه و ارتقا از نسخه قبلی روی دستگاه‌های واقعی آزمایش شود.
- [ ] ورود، نشست، مسیرهای اصلی، قطع اینترنت، بازگشت از پس‌زمینه و به‌روزرسانی سرویس‌کار آزمایش شوند.
- [ ] نسخه آزمایشی با برچسب test/prerelease باقی بماند و به‌عنوان انتشار تجاری معرفی نشود.

## 6. شواهد نهایی لازم
- [ ] CI موفق روی commit انتشار.
- [ ] استقرار موفق و سلامت سرویس.
- [ ] گزارش آزمون دسترسی نقش‌ها و جداسازی شرکت‌ها.
- [ ] گزارش آزمون مالی و بازیابی پشتیبان.
- [ ] گزارش نصب/ارتقای دستگاه واقعی و تأیید امضای release.
- [ ] تأیید نهایی مالک محصول برای انتشار.

## موانع وابسته به اقدام مالک/مدیر
این موارد را توسعه‌دهنده به‌جای مالک انجام نمی‌دهد و نباید با مقادیر حدسی دور زده شوند:
- انتخاب و تأیید ایمیل حساب مالک اصلی؛
- تولید و نگهداری امن توکن بازیابی و کلید امضای انتشار؛
- تأیید هزینه‌های سرویس میزبانی و دسترسی به حساب‌های بیرونی؛
- تأیید مفاد قرارداد مالی و نمونه داده‌های واقعی؛
- اجرای آزمون روی دستگاه فیزیکی در اختیار مالک یا تیم آزمون.

**قاعده انتشار:** تا زمانی که موارد امنیتی، پشتیبان‌گیری، محاسبات مالی و امضای پایدار Android شواهد قبولی نداشته باشند، وضعیت باید «آماده آزمون/پیش‌انتشار» باشد، نه «آماده تجاری».
